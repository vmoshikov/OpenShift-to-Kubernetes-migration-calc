# Сценарий демо mk8s-calc

Длительность — 15–20 минут + вопросы. Данные — `demo/dump.json` (синтетический
стенд `shop`, 7 сервисов, 30 подов на ПРОМ), CLI-шаги — `demo/run.sh`.

## Какую проблему решаем (вступление, 2 мин)

При переезде с OpenShift на managed Kubernetes нужно заранее ответить: **сколько
и каких нод заказать под каждый стенд — DEV, IFT, ПСИ, ПРОМ**, и как перенести
манифесты. Сейчас это делается вручную в таблицах, и у ручного расчёта три
системные проблемы:

1. **Limits завышены.** Команды годами ставили limits «с запасом» — в 4–8 раз
   больше request. Методика считает кластер по сумме limits, поэтому этот
   «воздух» напрямую превращается в лишние ноды.
2. **Данные есть только с одного стенда.** Обычно дамп снимают с того стенда,
   к которому есть доступ, а посчитать нужно все четыре.
3. **Расчёт и манифесты живут отдельно.** Посчитали одно, перенесли другое:
   сжатые limits не доходят до манифестов, DeploymentConfig надо
   конвертировать руками, внутренний реестр OpenShift всплывает на запуске.

**mk8s-calc** считает все стенды по нашей методике (сумма Limits × коэффициент
Таблицы 2), подбирает безопасное сжатие завышенных limits, показывает эффект
в ядрах/GiB/нодах/% и генерирует манифесты, согласованные с расчётом.
Результат — машиночитаемый план, на который дальше опирается агент миграции.

> Ключевая фраза: «Не просто калькулятор нод, а воспроизводимый план
> переезда: расчёт → решение по limits → манифесты → проверка».

## Подготовка (до демо)

```bash
go build -o mk8s-calc .
./mk8s-calc -ui=127.0.0.1:8080      # оставить запущенным, открыть в браузере
./demo/run.sh 1                     # прогреть, проверить, что всё собирается
```

- Открыть `demo/dump.json` в редакторе — понадобится вставить в UI.
- Шрифт терминала крупнее; окно браузера и терминала рядом.
- LLM-ревью — только если заранее проверен `OPENAI_API_KEY` (см. «Опционально»).

## Ход демо

### Шаг 1. Исходные данные и базовый расчёт (3 мин) — UI

**Показать:** в UI источник `paste`, вставить `demo/dump.json`, стенд-источник
ПРОМ, все интенсивности `off` → «Посчитать».

**Говорить:**
- Это обычный `oc get deployments,deploymentconfigs,statefulsets -o json` —
  доступ к кластеру агенту не нужен, дамп можно передать из закрытого контура.
- Блок «Предупреждения по данным»: DeploymentConfig, выключенный сервис
  `legacy-reports` (replicas=0, без requests/limits). Сервис сам находит
  то, что искажает расчёт.
- Таблица методики, ПРОМ: **V = 48 ядер**, коэффициент 1.36 из диапазона
  `32 < V ≤ 64` (6-я колонка — видно, откуда взят коэффициент) →
  **5 × 16 vCPU / 32 GiB**.
- Раскрыть «Все варианты перебора»: 4 варианта (8/16 vCPU × RAM ×2/×4),
  выбран самый плотный — минимум нод, потом минимум RAM.

**Ожидаемые цифры (ПРОМ, off):** V 48.00 ядер, RAM 78 GiB, 5 нод, 80 ядер / 160 GiB.

### Шаг 2. Override: убираем «воздух» из limits (4 мин) — UI

**Показать:** для всех стендов интенсивность `auto` → «Посчитать».
Таблица «Эффект override».

**Говорить:**
- `orders-api` просит 0.5 ядра, а limit — 2 ядра (×4). Override сжимает такие
  limits до разумного множителя от request. Уровни: soft / medium / hard.
- `auto` перебирает уровни и берёт **самый мягкий, который реально уменьшает
  кластер**. Смотрите — решение разное по стендам:

| Стенд | auto выбрал | Почему | Эффект |
|---|---|---|---|
| ПРОМ | soft | уже soft даёт минимум нод | **5 → 3 ноды (−40%)**, 80 → 48 ядер |
| ПСИ | medium | soft не уменьшает число нод, medium — да | 3 → 2 ноды (−33%) |
| IFT | **off** | сжатие не меняет ёмкость | limits не трогаем — нет выигрыша, нет риска |
| DEV | soft | нод столько же, но хватает 8 vCPU | ёмкость −50% (16 vCPU → 8 vCPU) |

- Итого по стендам: **10 → 7 нод (−30%)**, ёмкость 160 → 96 ядер (−40%).
  Только ресурсы и проценты — без денег, их считает финансовая модель.
- IFT — важный момент: сервис **не сжимает limits ради красивой цифры**.
  Нет выигрыша по нодам — значит, не рискуем троттлингом и OOM.

### Шаг 3. Данные с другого стенда + честный риск (3 мин) — терминал

```bash
./demo/run.sh 3
```

**Говорить:**
- Дамп сняли с ПСИ, а не с ПРОМ (`-from=psi`) — реплики ПРОМ пересчитываются
  от него: 30 подов ПСИ → 45 подов ПРОМ.
- Здесь `auto` выбрал `hard`: ноды 6 → 3 (−50%).
- **Но посмотрите на `search`:** это Java с `-Xmx6g`, а hard сжал memory limit
  до **4916Mi**. В проде такой сервис упадёт с OOMKilled.
- Вывод, который мы закладываем в архитектуру: `auto` оптимизирует ёмкость,
  но не знает про JVM и реальную нагрузку. Поэтому:
  1. решение по override **утверждает человек** (в плане видны все кандидаты);
  2. следующий шаг — метрики Prometheus p95/p99: сжатый limit не ниже
     фактического пика, CPU с троттлингом не сжимать.

> Этот шаг стоит показывать обязательно — он снимает вопрос «а не сломает ли
> оно прод» раньше, чем его зададут, и объясняет roadmap.

### Шаг 4. Манифесты, согласованные с расчётом (3 мин) — терминал или UI

```bash
./demo/run.sh 4
```
(в UI — кнопка «Скачать манифесты (zip)», предупреждения в `WARNINGS.txt`)

**Говорить:**
- Для каждого стенда — Namespace + workload'ы: `demo/out/<стенд>/<kind>/`.
- `orders-api` был **DeploymentConfig — стал Deployment**; CPU limit 2 → 1
  (то самое сжатие из расчёта), исходное значение сохранено в аннотации
  `mk8s-calc/original-limits` — ревьюер видит, что и почему поменялось.
- Image, env, probes сохранены; `status`, `uid`, `managedFields` и
  аннотации `openshift.io/*` вычищены.
- Предупреждения, которые обычно всплывают на запуске:
  образ `billing` во **внутреннем реестре OpenShift** (недоступен из managed K8s),
  **триггеры DC** не переносятся, **StorageClass** у redis
  (`ocs-storagecluster-ceph-rbd`) на новом кластере другой.

### Шаг 5. План для агента (2 мин) — терминал

```bash
./demo/run.sh 5
```

**Говорить:**
- Всё, что видели, доступно машиночитаемым JSON (`-json` или POST `format=json`
  в UI): версия схемы и методики, кандидаты override, эффект, поштучный план.
- Поле `basis.usage_metrics = not_connected` — план **сам честно говорит**,
  что посчитан по limits, без фактической нагрузки.
- Это контракт для агента: агент не считает сам (LLM не должна заниматься
  арифметикой) — он вызывает детерминированные инструменты, объясняет
  результат и собирает подтверждение человека.

### Шаг 5a. Baremetal: раскладка подов (3 мин) — UI

**Показать:** источник `paste`, вставить `demo/dump-baremetal.json`
(88 сервисов, 464 пода ПРОМ: 360 мелких API-подов, средние сервисы,
крупные аналитические поды), `auto` на ПРОМ, профиль OLTP → таблица
«Подбор baremetal», раскрыть «Все конфигурации серверов».

**Говорить:**
- Методика по V не видит размер подов. Здесь поды раскладываются по серверам
  с учётом лимита 110 подов на ноду, резервов, разнесения реплик и N+1.
- На крупных серверах (96–128 ядер) узкое место — **число подов**, а не CPU:
  мелкие поды упираются в 110/нода, 128 ядер загружены на ~23%.
- ПРОМ, OLTP: **13 × bm-32c-256g** (12 + 1 N+1), уплотнение CPU ×1.25.
  Переключить профиль на DWH → 10 серверов, уплотнение ×1.67.
  Профиль приложения задаёт, насколько плотно можно укладывать.
- etcd ограничивает кластер целиком, а не ноду — при превышении сервис
  предлагает делить на несколько кластеров.

### Шаг 6. Куда движемся (2 мин)

Схема агента: LLM оркестрирует, расчёты — детерминированные инструменты.

```
дамп стенда → анализ данных → calc_plan → recommend_override
     → [человек утверждает] → generate_manifests → validate (dry-run)
     → ревью (LLM) → переезд → сверка с фактом (Prometheus)
```

Roadmap:
1. Метрики Prometheus p95/p99 (запросы уже подготовлены, `prometheus.go`) —
   override по реальной нагрузке; троттлинг и OOMKilled — даже без истории.
2. Маскирование секретов перед отправкой в LLM.
3. Перенос LimitRange/ResourceQuota, учёт ClusterResourceOverride OpenShift.
4. MCP-сервер/API с инструментами для агента.

## Опционально (если есть `OPENAI_API_KEY`)

- **llm-paste:** в UI источник `llm-paste`, вставить произвольный текст
  (кусок `oc describe dc`, таблицу из Confluence) — модель извлечёт деплойменты.
- **Ревью плана:** чекбокс «ревью плана LLM» — модель ищет риски
  (в промпте явно сказано, что базис — limits, без метрик).

## Вопросы, к которым стоит быть готовым

**Почему считаем по limits, а не по requests?**
Так устроена наша методика: limits — пиковая заявленная нагрузка, коэффициент
Таблицы 2 даёт запас на сервисные расходы. Планировщик K8s размещает поды по
requests, поэтому оценка по limits консервативная.

**Почему почти всегда 16 vCPU?**
Критерий «минимум нод» выигрывает у 8 vCPU всегда, кроме очень маленьких стендов
(V ≤ 7.8 ядра и RAM ≤ 64 GiB). RAM ×4 выбирается, когда памяти больше
~2 GiB на ядро кластера.

**Не сломает ли override прод?**
Может — шаг 3 это показал. Поэтому: auto выбирает самый мягкий уровень,
отбрасывает уровни, при которых кластер растёт, решение утверждает человек,
а следующим шагом добавляем проверку по фактической нагрузке.

**Откуда метрики?**
В OpenShift встроенный Prometheus (`openshift-monitoring`, thanos-querier,
роль `cluster-monitoring-view`) — ~15 дней истории. Без него — троттлинг и
OOMKilled из cAdvisor и статуса подов, но без перцентилей.

**Что с безопасностью данных?**
Расчёт и манифесты — локально. В LLM уходит только сводка (`-review`) или
то, что пользователь сам вставил в `llm-paste`. Маскирование секретов — в roadmap.
Для закрытого контура — любой OpenAI-совместимый self-hosted эндпоинт
(`OPENAI_BASE_URL`).

## Если что-то пошло не так

- UI не открывается — `./mk8s-calc -ui=127.0.0.1:8080` запущен? Порт занят —
  другой порт.
- Нет Python для `run.sh` шагов 3–5 — показать файлы в `demo/out` и
  `./mk8s-calc -source=paste -override=auto -json < demo/dump.json`.
- Резервный путь без дампа — источник `mock` в UI (10 сервисов × 10 реплик):
  ПРОМ `auto` → hard, 6 → 5 нод.
