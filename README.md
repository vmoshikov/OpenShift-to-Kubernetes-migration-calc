# mk8s-migration-demo

Демо-агент (Go, только stdlib) для миграции с OpenShift (коммунальные
кластера) на managed Kubernetes. Три режима:

- **sizing** (по умолчанию) — расчёт capacity с эмуляцией контуров
  DEV / IFT (тест) / ПСИ (приёмка) / ПРОМ по методике «сумма Limits ×
  коэффициент Таблицы 2», override limits, генерацией манифестов и
  опциональным ревью плана OpenAI-совместимой моделью.
- **transform** (`-transform`) — конвертация OpenShift-специфичных сущностей
  в K8s-эквиваленты (Workstream 1 общей архитектуры агента миграции).
- **ui** (`-ui`) — минимальный веб-UI (одна HTML-форма, без JS/CSS-фреймворков)
  поверх sizing-режима: источник данных, ручной ввод (paste/llm-paste), контур,
  ревью — прямо в браузере, без консоли.

## Сборка

```bash
go build -o mk8s-calc .
```

Зависимостей вне стандартной библиотеки нет — модуль собирается офлайн.

## Источники данных (`-source`)

- `mock` (по умолчанию) — синтетический стенд: 10 деплойментов x 10 реплик
  с неоднородными requests/limits (`mock.go`), для демонстрации без доступа
  к реальному кластеру.
- `kubectl` / `oc` — читает реальные Deployment'ы через
  `kubectl get deployments -A -o json` / `oc get deployments -A -o json`
  (нужен настроенный `~/.kube/config` или `oc login`). Флаг `-namespace`
  сужает выборку до одного неймспейса.
- `paste` — ручной ввод без доступа к кластеру: вставляете в stdin тот же
  JSON, что вернул бы `oc/kubectl get deployments -A -o json`, и завершаете
  ввод `Ctrl+D`. Для закрытых контуров, где нельзя дать агенту прямой доступ
  к API кластеру, но можно снять и передать дамп.
- `llm-paste` — ручной ввод произвольным текстом: вставляете в stdin что
  угодно похожее на выгрузку ресурсов (`oc get all`, `oc describe dc`,
  таблицу requests/limits, кусок YAML), `Ctrl+D` — и LLM (тот же
  OpenAI-совместимый эндпоинт, что и `-review`) сама извлекает из этого
  список деплойментов с их requests/limits. Нужен `OPENAI_API_KEY`.

## Запуск

```bash
# расчёт по всем контурам на синтетических данных
./mk8s-calc -source=mock -env=all

# только ПРОМ, с реального стенда через oc, плюс ревью моделью
export OPENAI_API_KEY=...
export OPENAI_BASE_URL=https://your-endpoint/v1   # опционально, свой эндпоинт
export OPENAI_MODEL=gpt-4o-mini                   # опционально
./mk8s-calc -source=oc -namespace=my-app -env=prom -review

# ручной ввод: вставить JSON-дамп деплойментов и посчитать
./mk8s-calc -source=paste -env=all
# (вставить JSON, Ctrl+D)

# ручной ввод: вставить произвольный текст, распознать через LLM
./mk8s-calc -source=llm-paste -env=all
# (вставить любой текст с описанием деплойментов, Ctrl+D)
```

## Веб-UI (`-ui`)

```bash
./mk8s-calc -ui=127.0.0.1:8080
# открыть http://127.0.0.1:8080 в браузере
```

Одна страница: выбор источника (`mock`/`paste`/`llm-paste`), textarea для
ручного ввода, выбор контура, override по стендам, чекбокс ревью — и
таблицы методики и эффекта override, те же, что в CLI. `kubectl`/`oc`-источники в UI не предлагаются
намеренно (UI задуман для случая без прямого доступа к кластеру — вставить
дамп руками); при таком доступе используйте CLI. Слушает только на указанном
адресе — по умолчанию не поднимается и не слушает `0.0.0.0`, пока явно не
указать такой адрес.

## Методика: сумма Limits × коэффициент Таблицы 2 (основной расчёт)

1. **Базис V** — сумма CPU limits всех подов контура в ядрах, спрос по памяти —
   сумма memory limits в GiB. Реплики пересчитываются от стенда-источника
   (`-from`), override уже применён, пропущенные контуры не считаются.
   Если limits у контейнера не задан, берётся requests.
2. **Размер кластера** = V × коэффициент (зависит от диапазона V и ноды):

   | Диапазон V (ядер) | Нода 8 vCPU | Нода 16 vCPU |
   |-------------------|-------------|--------------|
   | V ≤ 16            | 2.05        | 1.50         |
   | 16 < V ≤ 32       | 1.61        | 1.50         |
   | 32 < V ≤ 64       | 1.45        | 1.36         |
   | 64 < V ≤ 256      | 1.35        | 1.27         |
   | 256 < V ≤ 512     | 1.34        | 1.26         |
   | V > 512           | 1.33        | 1.25         |

3. **Нод** = `ceil(размер / ядер ноды)`, не менее 2. Если RAM на этих нодах
   не покрывает спрос, нод добавляется до покрытия (помечается «под RAM»),
   так что каждый вариант рабочий.
4. **RAM ноды** = ядра × 2 или × 4 GiB.
5. **Перебор** {8, 16 vCPU} × {×2, ×4} → 4 варианта. Берётся самый плотный:
   минимум нод → наименьший номинальный RAM → выше плотность по CPU.

Для каждого варианта выводятся ёмкость (ядра / GiB) и плотность
(V / ядра ёмкости, спрос RAM / RAM ёмкости). В UI 6-й колонкой — диапазон V,
из которого взят коэффициент; под таблицей раскрываются все 4 варианта.

**Эффект override** считается той же методикой на исходных limits
(без override) и на сжатых: «было → стало (−Δ, −%)» по V, спросу RAM,
числу нод и ёмкости кластера (ядра, GiB) — по каждому контуру и итого.
Без денег, только ресурсы и проценты.

Ограничения: агрегатная оценка без bin-packing (поды > ~25% ноды могут
ложиться хуже); RAM ноды — только ×2/×4.

## Машиночитаемый план (`-json`) и HTTP-API

`-json` печатает в stdout план целиком: по контурам — методика и все
варианты, рекомендация override с кандидатами, эффект (было/стало/%),
поштучный план по деплойментам (реплики, limits до/после), предупреждения
по данным, поле `basis` (на чём основан расчёт и что даст Prometheus).
В отчёте есть `schema_version` (версия JSON-контракта) и `methodology`
(название, версия, таблица коэффициентов, типоразмеры нод, правило выбора,
коэффициенты реплик) — чтобы было видно, по какой методике посчитан план;
по каждому контуру — фактически применённые `override_rules`.
Тот же JSON отдаёт веб-UI на POST с `format=json` — готовый контракт для
агента/оркестратора.

```bash
./mk8s-calc -source=paste -from=psi -override=auto -json < dump.json > plan.json
```

## Генерация манифестов (`-manifests`)

```bash
./mk8s-calc -source=oc -namespace=shop -override=auto -manifests=./out
```

Пишет `<out>/<контур>/namespace/<ns>.yaml` и
`<out>/<контур>/<kind>/<ns>-<name>.yaml` для каждого посчитанного контура
(в веб-UI — кнопка «Скачать манифесты (zip)», предупреждения в
`WARNINGS.txt`): исходный объект из дампа (image, env, probes, volumes) с
пересчитанными `replicas` и сжатыми limits; `status`, `uid`,
`resourceVersion`, `managedFields`, `last-applied` и `openshift.io/*`
вычищаются. DeploymentConfig конвертируется в Deployment. В аннотациях
`mk8s-calc/*` — контур, реплики источника, уровень override и исходные
limits. Для mock/llm-paste (нет исходного объекта) — скелет с
`image: REPLACE_ME`. Предупреждения: образы из внутреннего реестра
OpenShift, DC-триггеры, `volumeClaimTemplates`/StorageClass, плюс
самопроверка манифеста: нет selector/контейнеров/image, limit < request.
Это не замена `kubectl apply --dry-run=server` на целевом кластере.

Источник `oc`/`kubectl` читает Deployment, StatefulSet и (для `oc`)
DeploymentConfig. Если в контейнере задан limit без request, request
считается равным limit (семантика K8s).

## Prometheus p95/p99 — что нужно доработать

Сейчас базис — limits из манифестов, т.е. то, что команды вписали, а не
реальное потребление. Заготовка — `prometheus.go` (`UsageStats`, PromQL,
`FetchUsage` возвращает «не реализовано»); точки встраивания помечены
`TODO(prometheus)` в коде:

- **базис V** (`plan.go`) — p95 CPU / p99 memory working set как проверка
  limits сверху (limits > p99 × 3 — «воздух»);
- **override** (`types.go`, `recommend.go`) — сжатый limit не ниже
  p99 × 1.2, память — от максимума (превышение = OOMKill); при CPU
  throttling > 5% CPU limit не сжимать;
- **реплики** (`plan.go`) — для HPA брать `max_over_time` числа реплик,
  а не `spec.replicas` на момент дампа;
- **BestEffort** — базис из фактического потребления;
- **манифесты/ревью** — p99 в аннотацию и в промпт модели.

Источник на OpenShift — thanos-querier в `openshift-monitoring`, токен
`oc whoami -t` или SA с `cluster-monitoring-view`; окно — от 14 дней.

## Ревью плана (`-review`)

Сводка методики по контурам уходит в OpenAI-совместимый `/chat/completions`
с промптом «проверь план на риски» (нехватка ресурсов, агрессивный override,
отказоустойчивость); ответ модели печатается после расчёта.

### Стенд-источник (`-from`)

Данные можно снять с любого стенда, не только с ПРОМ. `-from=dev|ift|psi|prom`
(по умолчанию `prom`) говорит, откуда дамп; реплики целевого контура
пересчитываются как `replicas × ReplicaFactor(цель) / ReplicaFactor(источник)`
(с минимумом `MinReplicas`). Считать можно и один контур: `-env=psi`.
Флаг `-skip=dev,ift` исключает контуры из расчёта. В UI — селект
«Данные сняты со стенда» и чекбокс «Пропустить» по каждому контуру.

### Override — сжатие limits к requests

Помимо requests калькулятор считает сумму limits по контуру (базис
«сумма Limits»). Если у контейнера `limits/requests` выше порога, limits
пересчитываются в `max(requests, floor) × цель` — только в сторону
уменьшения. Floor по умолчанию 250m CPU / 256Mi памяти. Интенсивность
задаётся по каждому контуру отдельно:

| Уровень  | Порог | Цель |
|----------|-------|------|
| `off`    | —     | —    |
| `soft`   | ×3.0  | ×2.0 |
| `medium` | ×2.0  | ×1.5 |
| `hard`   | ×1.5  | ×1.2 |
| `custom` | из `-override-{cpu,mem}-{ratio,target}` | |
| `auto`   | подбирается `RecommendOverride` | |

Порог и цель задаются пресетом; свои числа — только для `custom`
(в UI — свёрнутый блок «Тонкая настройка»). Пример: request 100m,
limit 2000m, порог 2, цель 1.5, floor 250m → 2000/100 = 20 > 2 →
max(100, 250) × 1.5 = 375m. Floor защищает от нереально малых limits
у контейнеров с крошечным request.

`auto` перебирает off/soft/medium/hard и берёт самый мягкий уровень с
наименьшей ёмкостью кластера (нод → ядер → RAM); уровни, при которых
расчётный кластер растёт (немонотонность Таблицы 2), исключаются. Если
сжатие не уменьшает ёмкость — остаётся `off`: сжимать limits без выигрыша
значит зря рисковать троттлингом и OOMKill.

```bash
# soft везде, hard на ПРОМ, без override на DEV; данные сняты с ПСИ
./mk8s-calc -from=psi -override=soft,prom:hard,dev:off
```

Floor — `-override-cpu-floor` / `-override-mem-floor`. В UI для каждого
контура свой уровень, порог/цель/floor по CPU и памяти; контур с включённым
override помечается в таблице `★override`, рядом с Limits — «было».

## Трансформация сущностей (`-transform`)

```bash
export KUBECONFIG=...   # oc login / контекст на исходном OpenShift-кластере
./mk8s-calc -transform=all -namespace=my-app -out=./transformed
```

- `-transform=routes` — Route → `networking.k8s.io/v1` Ingress.
  `edge`/`reencrypt` TLS помечается предупреждением (нужен реальный Secret
  с сертификатом), `passthrough` — аннотацией
  `nginx.ingress.kubernetes.io/ssl-passthrough` под ingress-nginx.
- `-transform=dc` — DeploymentConfig → `apps/v1` Deployment. Триггеры
  ImageChange/ConfigChange не переносятся (их нет в Deployment) — образ
  дальше обновляется через CI/CD, а не автоматически при пуше в ImageStream.
- `-transform=scc` — SecurityContextConstraints → Pod Security Admission
  labels на Namespace (`pod-security.kubernetes.io/{enforce,audit,warn}`).
  Сопоставление SCC → PSA грубое (PSA умеет меньше нюансов, чем SCC) —
  для каждого namespace берётся самый широкий уровень среди всех SCC,
  выданных его serviceaccount'ам.
- `-transform=all` — все три конвертации разом.

Источник — только `oc` (Route/DeploymentConfig/SCC есть лишь на OpenShift).
Манифесты пишутся в `<out>/<kind>/<namespace>-<name>.yaml` (валидный JSON —
это подмножество YAML, `kubectl apply -f` принимает такие файлы). После
конвертации печатается список предупреждений — мест, требующих ручного
ревью инженера (TLS-секреты, image triggers, кастомные SCC и т.д.).

## Ограничения демо (что дорабатывать для боевого агента)

- Методика — агрегатная (сумма limits × коэффициент), а не honest
  bin-packing по подам — поды крупнее ~25% ноды могут ложиться хуже.
- `ReplicaFactor`/`MinReplicas` по контурам — дефолтные предположения
  (`profiles.go`), их нужно сверить с реальной практикой клиента.
- Трансформация Route/DC/SCC — эвристическая (см. предупреждения в выводе);
  не покрыты BuildConfig/ImageStream, кастомные admission-хуки, NetworkPolicy
  из EgressNetworkPolicy и т.п. — это расширение того же Workstream 1.
